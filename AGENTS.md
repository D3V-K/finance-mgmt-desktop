# Parallel implementation guide

This repository is the **new, single-user, fully offline** finance desktop app. Use Tauri 2, Svelte/TypeScript, Rust, and SQLite. The existing [frontend](https://github.com/D3V-K/finance-mgmt-frontend) and [Python backend](https://github.com/D3V-K/finance-mgmt-backend-lite) are behavior references, **not** components to bundle. The [desktop epic](https://github.com/D3V-K/finance-mgmt-desktop/issues/1) tracks the work; each issue has its own acceptance criteria.

## First supported OS and approved first slice

**macOS is the first supported target**, using Tauri's WKWebView. Validate a clean-checkout launch and the #3 prototype in a real macOS Tauri window before marking #3/#4 complete; the merged scaffold renders `src/` while the synthetic prototype lives in `prototype/`, so arrange an explicit temporary integration or subsequent #12 integration for that test. Check modal focus/Esc, date entry, shortcuts versus the app menu, Japanese text/IME, number/date formatting, VoiceOver and keyboard navigation, themes, reduced motion, resizing, charts and CSP. Record macOS version, architecture, results and fixes. Windows and Linux remain future validation targets.

The integrator approves the **first-slice contract and conventions** in [`docs/contracts/v1-core-ledger.md`](docs/contracts/v1-core-ledger.md), based on [`docs/parity/v1-feature-matrix.md`](docs/parity/v1-feature-matrix.md) and `fixtures/parity/v1/`. This is not approval of a concrete SQLite DDL or full parity; Codex and Claude must review the shared boundary before their implementation branches diverge. The human maintainer retains merge and release decisions.

## Sequence and parallel work

1. **Wave 1 — foundation and handoff:** The integrator supplies #2's initial feature matrix and Python golden cases. Claude completes #3's macOS WKWebView validation and #4's clean-checkout launch, building on merged PRs #17/#18. The first slice and conventions are in the linked v1 contract. Full #2 acceptance still requires expanded fixtures and exact-pin/PostgreSQL verification; distinguish implemented code from feature-flagged or merely proposed behavior.
2. **Wave 2 — coordinated foundation:** Codex proposes #5 migrations for review against v1 before applying them; Claude implements #6 against the same contract. Codex starts #7 after model/boundary review. Claude may build #12 against fixtures and mocks but cannot complete it before the real #7/#8 paths. Codex may start #15 after #5. Merge migrations and contract definitions before consumers; Claude wires domain/database operations into Tauri commands without duplicating financial logic.
3. **Wave 3 — feature lanes:** After #7 lands, Codex handles #8–#11 in small PRs and develops #14 export/schema mapping and #15 backup/restore in separate branches. Claude implements #12/#13 screens and command adapters. Coordinate card schedules (#9) with dependent forecast/reconciliation work (#10/#11). #8 is needed to finish #12. #14 cannot be accepted before full schema, relationship and financial verification.
4. **Wave 4 — integration:** Claude handles #16 after domain parity, real-command UI paths, verified import and backup/restore. Codex supplies financial/import verification and fixes data-layer release blockers; Claude owns packaged-app offline tests. The human maintainer decides merge order/release readiness; no agent silently retires AWS resources.

## Collaboration protocol

- Work in **separate worktrees/branches**, preferably one issue per branch (`codex/5-sqlite-schema`, `codex/7-core-ledger`, `claude/6-local-boundary`, `claude/12-core-ui`). Never let multiple agents modify the same working tree. Open small PRs targeting the current default branch, reference the issue, and list tests, assumptions, contract changes, and remaining gaps.
- Codex owns migration files, database/import/backup logic, domain calculations and parity fixtures; Claude owns Tauri command registration/transport, security, build/release configuration and UI components/styles. A change to a shared contract or schema requires review from the other owner **before** implementation branches diverge. Do not independently rename commands, alter the DB schema, or edit the same shared files. Coordinate cross-layer changes in a reviewed contract PR before dependent implementation PRs.
- Keep a versioned typed frontend-to-Tauri command contract in the repo once #4 creates the structure. Proposed changes should state Rust input/output types, TypeScript equivalents, errors, money units, date/time-zone meaning, null/incomplete semantics, and whether a write is idempotent. Do not create a second local HTTP backend just to reuse the old API.
- Use #2's golden fixtures as the authority for financial parity. Require Rust unit/integration tests on real SQLite migrations, frontend tests for accessible behavior, and at least one packaged-app offline end-to-end test before calling a feature done. Mocked UI success alone is not enough.
- Integrate frequently. A PR depending on another PR should say so explicitly; rebase or merge the updated default branch after the dependency lands. Do not merge generated schema, frontend, and domain changes independently if the contracts differ. The maintainer resolves conflicting assumptions, not whichever agent merges first.
- Preserve JPY integer amounts, stable IDs, legacy/canonical separation, card-debt signs, correction/audit links, unknown dates, incomplete balances, and the distinction among spending, transfers, repayment, earmarking, and future forecasts. The legacy net-balance series is **not** true net worth.
- No Cognito/login, cloud dependency, telemetry, or network requirement in the installed app. Use scoped Tauri permissions and local commands. Back up Aurora before import; select a source user explicitly, never merge users implicitly; validate counts, balances, reports, and relationships before accepting data. Do not shut down AWS until an imported database and restored backup are verified.
